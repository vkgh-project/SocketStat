# Оновлення SocketStat на PythonAnywhere

Сайт: **https://vacula.eu.pythonanywhere.com**. Код: [vkgh-project/SocketStat](https://github.com/vkgh-project/SocketStat), гілка `main`.

Після одноразового налаштування: відправте зміни на GitHub → відкрийте **«Оновлення системи»** внизу панелі → натисніть **«Оновити з GitHub»**. Сторінка доступна за адресою `/updates` з тим самим логіном і паролем, що й панель.

## Одноразове встановлення та прибирання

Чинний сайт запускає `/bin/bash /home/Vacula/start.sh`. Цей файл переходить у `/home/Vacula` та використовує `/home/Vacula/.venv/bin/python`. Папка `/home/Vacula/socketstat` містить Python-пакет, а не окреме віртуальне середовище.

Перед встановленням перевірте **серверний `/home/Vacula/.env`**: він має містити чинні ключі Tuya, ID розеток, `DASHBOARD_USER`, `DASHBOARD_PASSWORD` від 12 символів і правильний `DB_PATH`. Типова база — `/home/Vacula/data/socketstat.db`. Не копіюйте шаблон поверх налаштованого `.env` і не змінюйте шлях до чинної історії. Якщо раніше налаштування задавалися лише через `export` у `start.sh`, перенесіть їх у цей `.env`: новий launcher використовуватиме файл.

На сторінці PythonAnywhere **Account → API token** створіть токен, якщо його ще немає. PythonAnywhere надає його процесам через `API_TOKEN`; за потреби можна явно додати `PYTHONANYWHERE_API_TOKEN` до серверного `.env`. Не публікуйте токен. Перезапуск використовує [офіційний ASGI API](https://help.pythonanywhere.com/pages/ASGIAPI/).

У **Bash console** виконайте:

```bash
curl -fL https://raw.githubusercontent.com/vkgh-project/SocketStat/main/update_pythonanywhere.sh -o /home/Vacula/update_pythonanywhere.sh &&
bash /home/Vacula/update_pythonanywhere.sh --clean
```

Це одна команда встановлення з прибиранням. Скрипт:

1. Перевірить конфігурацію та доступ до PythonAnywhere API до зміни запуску.
2. Підготує чисту копію коду й окреме віртуальне середовище, поки старий сайт працює.
3. Зробить копію `.env`, узгоджений SQLite backup та копію старого `start.sh`.
4. Перемкне `start.sh` на готову версію та перезапустить сайт.
5. Дочекається успішного `/healthz` саме нової версії й лише тоді прибере старі файли з домашньої папки.

**Що означає `--clean`:** старі звичайні файли й папки в `/home/Vacula`, а також старі `.venv`, `.git` і `.pytest_cache`, спочатку потраплять у перевірений архів `legacy-*.tar.gz`, потім будуть видалені. Це стосується також інших звичайних файлів, які ви могли зберігати в домашній папці. Збережуться `.env` і його ціль, якщо це посилання, чинна база разом із її папкою/WAL, новий `start.sh`, папка `.socketstat` і службові приховані файли акаунта (`.ssh`, `.local`, `.bashrc` тощо). Якщо база лежить усередині старої папки коду, ця папка теж буде збережена. Буквально видаляти весь HOME не потрібно для чистого встановлення.

Щоб спочатку налаштувати оновлення без прибирання, запустіть ту саму команду **без `--clean`**. Після успішного встановлення можна окремо переглянути точний перелік зайвих файлів:

```bash
/home/Vacula/.socketstat/current/.venv/bin/python /home/Vacula/.socketstat/current/deploy_pythonanywhere.py cleanup
```

Щоб застосувати показаний перелік, повторіть цю команду з `--apply`.

## Подальші оновлення

1. Після розробки відправте перевірені зміни в GitHub, гілку `main`.
2. Відкрийте [сторінку оновлень](https://vacula.eu.pythonanywhere.com/updates).
3. Натисніть **«Оновити з GitHub»** та дочекайтеся повідомлення про завершення.

Система автоматично підготує нову версію й залежності в окремій папці, перевірить налаштування, зробить backup, перемкне версію та перезапустить сайт. Підготовка не зупиняє збір даних. Коротка перерва відбувається лише під час перезапуску; її тривалість залежить від PythonAnywhere. Паралельні оновлення заблоковані. Якщо перевірка чи встановлення залежностей не пройшли, чинна версія продовжує працювати.

`.env` та SQLite не завантажуються з GitHub і не замінюються. Зберігається їхній чинний шлях; відносний `DB_PATH` і надалі рахується від `/home/Vacula`. Перемикання версії не відновлює стару БД, тому записи, додані під час підготовки, залишаються. Звичайне очищення спостережень старших за 14 діб продовжує діяти.

## Де лежать файли

```text
/home/Vacula/
├── .env                      чинна конфігурація
├── data/socketstat.db        чинна база (або інший DB_PATH)
├── start.sh                  стабільний запуск сайту
└── .socketstat/
    ├── current -> releases/… поточна версія
    ├── previous -> releases/… попередня версія
    ├── releases/             код і .venv кожної версії
    ├── backups/              копії .env, SQLite та старих файлів
    ├── deployment.json       параметри встановлення
    ├── state.json            стан оновлення
    └── update.log            приватний журнал
```

Зберігаються лише поточна й попередня версії коду та п’ять останніх резервних копій даних. Початковий архів старих файлів зберігається окремо: вони містять секрети та історію, не додавайте їх у GitHub. Контролюйте вільне місце: під час оновлення потрібне місце для двох середовищ, копії БД і, при першому прибиранні, архіву старих файлів. Самостійно видаляйте лише вже непотрібні резервні копії.

## Якщо сталася помилка

Сторінка показує етап і стан виконання. Подробиці — у `/home/Vacula/.socketstat/update.log` та журналах PythonAnywhere. Запуск оновлень потребує мережевого доступу вебпроцесу до GitHub, PyPI та PythonAnywhere API; обмежений тариф може блокувати ці адреси.

Якщо після перемикання нова версія не запускається, сторінка оновлення теж буде недоступна. PythonAnywhere може завершити й фоновий процес оновлення під час reload; тому автоматичний відкат не гарантується. У Bash console відновіть попередній код:

```bash
/home/Vacula/.socketstat/previous/.venv/bin/python /home/Vacula/.socketstat/previous/deploy_pythonanywhere.py rollback
```

Для самого першого встановлення попередньої керованої версії ще немає. Скрипт спробує відновити старий `start.sh`, якщо не дочекається працездатного сайту. Його резервна копія також є в `.socketstat/backups/<дата>/start.sh`; старі файли не прибираються до успішної перевірки нового сайту.

Відкат змінює код, а не історію. Не копіюйте резервну БД поверх активної. Для майбутніх змін схеми БД потрібні сумісні міграції; цей механізм не робить несумісні версії автоматично сумісними.
