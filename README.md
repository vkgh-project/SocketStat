# SocketStat

Моніторинг доступності **двох** розеток Smart Life через Tuya Cloud, щохвилини.
Один FastAPI-застосунок, SQLite, інтерфейс українською без Node.js та зовнішніх CDN.

## Можливості

- Незалежне опитування двох розеток, спільна часова вісь і окрема статистика.
- `online` / `offline` / `unknown`. Помилка API та пропущена перевірка — `unknown`.
- Світлий інтерфейс у стилі wireframe: компактні контурні блоки, яскраві синій та зелений кольори розеток на всіх графіках, окремі вкладки «Доступність», «За годинами», «Тижневий розклад», «Розетки» та «Звіт недоступності». Період спільний для всіх вкладок, вибрана вкладка зберігається під час оновлення даних. Перемикання вкладок — мишею або клавішами ← / →, Home / End після фокусування вкладки.
- Один спільний ступінчастий графік для двох розеток (тонкі синя та яскраво-зелена суцільні лінії на сітці): по горизонталі час, по вертикалі 1 — доступна, 0 — недоступна. Проміжки без даних показані розривами лінії. Часові діапазони 1 год, 6 год, доба, тиждень, 14 днів; підказки та таблиця недоступності.
- Графік за годинами доби: сума хвилин недоступності для кожної розетки за вибраний період, окреме штрихування хвилин без даних.
- Тижневий розклад: години 00–24 по горизонталі, дні Пн–Нд по вертикалі, дві смуги на годину для двох розеток; вибір тижня в межах періоду. Насиченість кольору показує недоступність, штрихування — відсутність даних. Усі групування — за часом Києва.
- Доступність серед відомих даних, покриття спостереженнями, сумарна й найдовша недоступність.
- Історія за останні 14 діб. Очищення при запуску та щогодини: фізично запис може залишатися до наступного очищення, але API не показує дані старші 14 діб.
- HTTP Basic авторизація, серверне зберігання ключів, автоматичне оновлення панелі кожні 30 с.

## Локальний запуск

Python 3.9+ (на Render використовується 3.12). Усі команди виконуйте з папки проєкту.

Віртуальне середовище `.venv` потрібно створювати окремо для кожної ОС. Не переносьте його між macOS і Windows: у macOS інтерпретатор міститься в `.venv/bin`, у Windows — у `.venv\Scripts`.

### Windows (PowerShell)

Якщо встановлено `uv`, створіть середовище з Python 3.12 і встановіть залежності:

```powershell
uv venv --python 3.12 .venv
uv pip install --python .\.venv\Scripts\python.exe -r requirements.txt
```

Якщо `uv` не встановлено, але доступний Python із командою `py`, використайте:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Якщо `.venv` вже перенесена з macOS, перед створенням Windows-середовища збережіть її під іншою, вільною назвою:

```powershell
Rename-Item .venv .venv-macos
```

Під час першого налаштування створіть `.env`, якщо його ще немає:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Заповніть `.env` за інструкцією нижче, потім запустіть застосунок:

```powershell
.\.venv\Scripts\python.exe -m uvicorn socketstat.app:app --host 127.0.0.1 --port 8000 --workers 1
```

Активація середовища не потрібна: команда прямо використовує його Python. Це також усуває помилку `uvicorn is not recognized`, коли команда `uvicorn` недоступна в `PATH`.

### Windows: запуск готового `.exe` без Python

1. Помістіть `SocketStat.exe` в окрему папку, доступну для запису, наприклад `Документи\SocketStat`.
2. Скопіюйте свій налаштований `.env` у цю папку. Якщо `.env` відсутній, перший запуск створить шаблон і попросить заповнити його. Секрети у виконуваний файл не включені.
3. Запустіть `SocketStat.exe` подвійним клацанням. Після запуску сервера відкриється браузер із http://127.0.0.1:8000; увійдіть із `DASHBOARD_USER` та `DASHBOARD_PASSWORD` із `.env`.
4. Залишайте консольне вікно відкритим для моніторингу. Для завершення натисніть `Ctrl+C`. Комп’ютер має працювати й мати доступ до інтернету; під час сну перевірки не виконуються.

За типового `DB_PATH=./data/socketstat.db` історія зберігається в папці `data` поруч із `.exe`, незалежно від папки, з якої його запущено. Для перенесення на інший комп’ютер потрібні `.exe`, `.env` і, за потреби, резервна копія історії. Запускайте лише один екземпляр для тієї самої пари розеток; одночасно запущений Python-сервер теж потрібно зупинити.

Додаткові параметри запуску з PowerShell:

```powershell
.\SocketStat.exe --port 8001
.\SocketStat.exe --no-browser
```

Якщо порт зайнятий, програма покаже помилку. Для тесту без Tuya використайте окрему папку з `.env`: `DEMO_MODE=true`, `DASHBOARD_USER=admin`, `DASHBOARD_PASSWORD` від 12 символів.

Збірка `.exe` з коду виконується на Windows у створеному Windows-середовищі `.venv`:

```powershell
uv pip install --python .\.venv\Scripts\python.exe -r requirements-build.txt
.\.venv\Scripts\python.exe build_windows.py
```

Без `uv` встановіть залежності командою `.\.venv\Scripts\python.exe -m pip install -r requirements-build.txt`. Результат — `dist/SocketStat.exe` та `dist/.env.example`. Python, бібліотеки та статичні файли включені в `.exe`; готовий файл призначений для Windows тієї самої архітектури, що й Python збірки (поточна збірка — x64).

### macOS (Terminal, zsh/bash)

Зі встановленим Python 3.9+ створіть середовище та встановіть залежності:

```sh
python3 -m venv .venv
./.venv/bin/python -m pip install -r requirements.txt
```

Під час першого налаштування створіть `.env`, якщо його ще немає:

```sh
if [ ! -e .env ]; then cp .env.example .env; fi
```

Заповніть `.env` за інструкцією нижче, потім запустіть застосунок:

```sh
./.venv/bin/python -m uvicorn socketstat.app:app --host 127.0.0.1 --port 8000 --workers 1
```

Активація середовища не потрібна. Якщо `.venv` перенесена з Windows, перед створенням macOS-середовища збережіть її під іншою, вільною назвою, наприклад `mv .venv .venv-windows`.

### Налаштування `.env` та робота з панеллю

Заповніть `.env` перед запуском на будь-якій ОС:

- `TUYA_CLIENT_ID`, `TUYA_CLIENT_SECRET` — Access ID / Access Secret хмарного проєкту.
- `TUYA_ENDPOINT` — endpoint **датацентру проєкту**, а не довільно вибраний регіон. За замовчуванням Central Europe: `https://openapi.tuyaeu.com`.
- `SOCKET_1_ID`, `SOCKET_2_ID` — різні Device ID прив’язаних розеток.
- `SOCKET_1_NAME`, `SOCKET_2_NAME` — назви для панелі.
- `DASHBOARD_USER`, `DASHBOARD_PASSWORD` — вхід до панелі, пароль від 12 символів.
- `DB_PATH` — файл SQLite, локально `./data/socketstat.db`.

Відкрийте http://127.0.0.1:8000 і введіть логін та пароль панелі.
Для наступних запусків достатньо виконати команду запуску для своєї ОС з папки проєкту. Зупинка — `Ctrl+C` у терміналі.
Для демо встановіть `DEMO_MODE=true` і задайте пароль панелі: Tuya-ключі та ID тоді не потрібні. Демо генерує лише нові спостереження під час роботи, історію заднім числом не вигадує. Для демо й реальних даних використовуйте різні файли БД.

Не використовуйте `--reload` для постійного моніторингу. Рівно **один процес / один worker**: збирач запускається через lifespan застосунку, декілька worker дублюватимуть запити до Tuya.

## Tuya

Smart Life має бути прив’язаний до проєкту. У Tuya API Explorer перевірте доступ до:

```text
GET /v1.0/token?grant_type=1
GET /v1.0/iot-03/devices/{device_id}
```

Потрібна відповідь з булевим `result.online`. `false` означає офлайн; відсутнє поле — `unknown`, а не офлайн. Значення реле `switch_1` не використовується для визначення доступності.

Якщо ваш проєкт не має прав на цей endpoint, надайте йому відповідний API-сервіс у Tuya. Код не робить запитів керування розетками. Авторизація підписується HMAC-SHA256, токен кешується в пам’яті, прострочений токен оновлюється. Транзитні мережеві помилки / HTTP 429 / 5xx мають один повтор; загальний ліміт перевірки — 40 секунд. Секрети й тіла відповідей не потрапляють у логи.

Орієнтовно 86 400 запитів деталей за 30 діб для двох розеток, додатково токени й повтори. Перевірте квоту та строк доступу Tuya IoT Core.

Офіційна документація:
- https://developer.tuya.com/en/docs/iot/new-singnature?id=Kbw0q34cs2e5g
- https://developer.tuya.com/en/demo/python-iot-development-practice

## Render

### Перший запуск через Blueprint

1. Закомітьте й завантажте код у свій Git-провайдер, включно з `render.yaml`, `requirements.txt` і папкою `socketstat/static`. Локальні `.env`, `.venv` та резервні копії середовищ на кшталт `.venv-macos` / `.venv-windows` у репозиторій не додавайте.
2. Підключіть репозиторій до Render через **New → Blueprint**, використовуючи `render.yaml` у корені репозиторію.
3. Blueprint створює **платний Web Service Starter** з Persistent Disk 1 GB. Перевірте актуальну вартість сервісу й диска перед створенням ресурсів.
4. Введіть значення змінних із `sync: false`: `TUYA_CLIENT_ID`, `TUYA_CLIENT_SECRET`, `SOCKET_1_ID`, `SOCKET_2_ID`, `DASHBOARD_PASSWORD`. Пароль панелі має містити щонайменше 12 символів, Device ID двох розеток мають відрізнятися.
5. Перевірте `TUYA_ENDPOINT`: у Blueprint задано Central Europe, але значення має відповідати датацентру вашого Tuya-проєкту. За потреби змініть `DASHBOARD_USER` (типово `admin`) і назви розеток. Для реального моніторингу `DEMO_MODE` має бути відсутнім або `false`.
6. Дочекайтеся успішного деплою. Відкрийте HTTPS-адресу сервісу та введіть логін і пароль панелі. Відкритий `/healthz` має повертати `{"status":"ok"}`. Історія починає накопичуватися після запуску; локальна БД автоматично не переноситься.

Значення з локального `.env` автоматично на Render не потрапляють: задайте їх у Render **Environment**. Файл SQLite й таблиці застосунок створює сам під час запуску; окрема команда міграції не потрібна.

### Якщо створюєте Web Service вручну

Використайте ті самі параметри, що й у `render.yaml`:

| Параметр | Значення |
| --- | --- |
| Runtime | Python |
| Root Directory | Корінь репозиторію; поле залишити порожнім |
| Plan | Starter або інший платний план із підтримкою диска |
| Build Command | `pip install -r requirements.txt` |
| Start Command | `uvicorn socketstat.app:app --host 0.0.0.0 --port $PORT --workers 1` |
| Health Check Path | `/healthz` |
| Persistent Disk | Mount Path `/var/data`, Size 1 GB |
| `PYTHON_VERSION` | `3.12.8`, як у `render.yaml` |
| `DB_PATH` | `/var/data/socketstat.db` |

Також додайте змінні Tuya та панелі, описані вище. Версію Python задавайте повністю, з номером патча. Команда Render виконується в Linux: використовуйте `$PORT` і `0.0.0.0`. Створювати чи активувати локальне Windows/macOS-середовище на Render не потрібно.

### Оновлення вже розгорнутого сервісу

Закомітьте зміни й завантажте їх у гілку, підключену до Render. Якщо автодеплой увімкнений, дочекайтеся його завершення; інакше запустіть **Manual Deploy → Deploy latest commit**. Останні зміни вкладок, кольорів і графіків потребують лише звичайного деплою: Node.js, збірка фронтенду та додаткові Python-залежності не потрібні.

Зберігайте диск `/var/data` і `DB_PATH=/var/data/socketstat.db` — тоді історія залишиться після деплою. Після оновлення перезавантажте сторінку через `Ctrl+F5` у Windows або `Cmd+Shift+R` у macOS. Якщо змінюєте змінні середовища в Render, застосуйте їх із деплоєм: **Save only** збереже значення, але поточний процес використає їх лише після наступного деплою.

Не використовуйте free-сервіс із тимчасовою файловою системою: він може засинати й не зберігатиме SQLite після перезапусків. Не виносьте збирач в окремий Render-сервіс: Persistent Disk не спільний між сервісами. Диск також означає коротку перерву під час деплою; пропущені хвилини залишаться невідомими.

`GET /healthz` — відкритий liveness endpoint без даних розеток. Він перевіряє БД і роботу задачі збору, але не вважає збій Tuya причиною перезапуску сервісу. `GET /api/dashboard?hours=24` — захищений API (1 ≤ hours ≤ 336). Панель і API мають `Cache-Control: no-store`. Basic Auth слід використовувати через HTTPS; Render надає HTTPS на публічній адресі.

Для резервних копій використовуйте SQLite backup API / команду `.backup`, а не просте копіювання лише основного файлу активної WAL-бази. Видалені записи звільняють місце для повторного використання; файл БД не обов’язково зменшується. 14 діб — строк зберігання робочої історії, а не гарантія стирання з резервних копій платформи.

Документація Render: [FastAPI](https://render.com/docs/deploy-fastapi), [Persistent Disks](https://render.com/docs/disks), [версія Python](https://render.com/docs/python-version), [змінні середовища](https://render.com/docs/configure-environment-variables).

## Як інтерпретувати історію

Один запис описує хвилинний слот UTC. Інтервали однакових станів об’єднуються; стан не переноситься через пропущені хвилини. Унікальний ключ `(device_id, scheduled_at)` захищає від повторного запису. У БД — Unix UTC, у панелі — `Europe/Kyiv` з урахуванням літнього часу.

Тривалість — оцінка за дискретними перевірками, межі округлено до хвилинних слотів. Фактичний час відповіді збережений окремо як `checked_at`. Перший слот після запуску може бути неповним. Недоступність через Tuya може відображатися із затримкою heartbeat, і не доводить відключення електроенергії: причиною також може бути Wi-Fi, домашній інтернет чи Tuya. Статус на картці стає невідомим після 120 секунд без свіжого спостереження. На графіку пропущений поточний слот одразу відображається як невідомий до завершення перевірки.

Якщо інтервал впирається в край видимого періоду, його справжній початок або завершення можуть бути за межами графіка. Безперервний офлайн, розділений пропуском даних, рахується як два спостережувані інтервали.

Прогнозування поки не реалізоване. Двотижнева історія дозволяє почати з аналізу коротких повторень; для довших закономірностей знадобиться окреме рішення про збереження агрегатів.

## Перевірки

Windows (PowerShell), після створення `.venv`:

```powershell
uv pip install --python .\.venv\Scripts\python.exe -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
```

Якщо середовище створене через `py` і ви працюєте без `uv`, для встановлення тестових залежностей використайте `.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt`.

macOS:

```sh
./.venv/bin/python -m pip install -r requirements-dev.txt
./.venv/bin/python -m pytest -q
```

Тести використовують тимчасові БД та підмінені HTTP-відповіді. Перевіряють пропуски, межі інтервалів, очищення, незалежність двох розеток, підпис запитів, оновлення токена та авторизацію. Для перевірки реального інтегрування потрібні ваші облікові дані Tuya; не передавайте їх у чат.

Додаткові перевірки групування графіків (не потрібні для запуску сервісу, Node.js 18+):

```sh
node --test tests/charts.test.cjs
```

Вони перевіряють поділ за київською північчю, часткові хвилини, пропуски, перехід на літній/зимовий час і побудову панелей без даних. Тижневий розклад використовує лише вибраний діапазон; решта тижня показана штрихуванням.
