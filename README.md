# SocketStat

Моніторинг доступності **двох** розеток Smart Life через Tuya Cloud, щохвилини.
Один FastAPI-застосунок, SQLite, інтерфейс українською без Node.js та зовнішніх CDN.

## Можливості

- Незалежне опитування двох розеток, спільна часова вісь і окрема статистика.
- `online` / `offline` / `unknown`. Помилка API та пропущена перевірка — `unknown`.
- Один спільний ступінчастий графік для двох розеток (оливкова суцільна та бурштинова пунктирна лінії): по горизонталі час, по вертикалі 1 — доступна, 0 — недоступна. Проміжки без даних показані розривами лінії. Часові діапазони 1 год, 6 год, доба, тиждень, 14 днів; підказки та таблиця недоступності.
- Графік за годинами доби: сума хвилин недоступності для кожної розетки за вибраний період, окреме штрихування хвилин без даних.
- Тижневий розклад: дні Пн–Нд, години 00–24, дві смуги на годину для двох розеток; вибір тижня в межах періоду. Насиченість кольору показує недоступність, штрихування — відсутність даних. Усі групування — за часом Києва.
- Доступність серед відомих даних, покриття спостереженнями, сумарна й найдовша недоступність.
- Історія за останні 14 діб. Очищення при запуску та щогодини: фізично запис може залишатися до наступного очищення, але API не показує дані старші 14 діб.
- HTTP Basic авторизація, серверне зберігання ключів, автоматичне оновлення панелі кожні 30 с.

## Локальний запуск

Python 3.9+ (на Render використовується 3.12).

```sh
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Заповніть `.env`:

- `TUYA_CLIENT_ID`, `TUYA_CLIENT_SECRET` — Access ID / Access Secret хмарного проєкту.
- `TUYA_ENDPOINT` — endpoint **датацентру проєкту**, а не довільно вибраний регіон. За замовчуванням Central Europe: `https://openapi.tuyaeu.com`.
- `SOCKET_1_ID`, `SOCKET_2_ID` — різні Device ID прив’язаних розеток.
- `SOCKET_1_NAME`, `SOCKET_2_NAME` — назви для панелі.
- `DASHBOARD_USER`, `DASHBOARD_PASSWORD` — вхід до панелі, пароль від 12 символів.
- `DB_PATH` — файл SQLite, локально `./data/socketstat.db`.

```sh
uvicorn socketstat.app:app --host 127.0.0.1 --port 8000 --workers 1
```

Відкрийте http://127.0.0.1:8000 і введіть логін та пароль панелі.
Для демо встановіть `DEMO_MODE=true` і задайте пароль панелі: Tuya-ключі та ID тоді не потрібні. Демо генерує лише нові спостереження під час роботи, історію заднім числом не вигадує. Для демо й реальних даних використовуйте різні файли БД.

Не використовуйте `--reload` для постійного моніторингу. Рівно **один процес / один worker**: збирач запускається через lifespan застосунку, декілька worker дублюватимуть запити до Tuya.

## Tuya

Smart Life має бути прив’язаний до проєкту. У Tuya API Explorer перевірте доступ до:

```text
GET /v1.0/token?grant_type=1
GET /v1.0/iot-03/devices/{device_id}
```

Потрібна відповідь з булевим `result.online`. `false` означає офлайн; відсутнє поле — `unknown`, а не офлайн. Значення реле `switch_1` не використовується для визначення доступності.

Якщо ваш проєкт не має прав на цей endpoint, надайте йому відповідний API-сервіс у Tuya. Код не робить запитів керування розетками. Авторизація підписується HMAC-SHA256, токен кешується в пам’яті, прострочений токен оновлюється. Транзитні мережеві помилки / HTTP 429 / 5xx мають один повтор; загальний ліміт перевірки — 40 секунд. Секрети й тіла відповідей не потрапляють у логи.

Орієнтовно 86 400 запитів деталей за 30 діб для двох розеток, додатково токени й повтори. Перевірте квоту та строк доступу Tuya IoT Core.

Офіційна документація:
- https://developer.tuya.com/en/docs/iot/new-singnature?id=Kbw0q34cs2e5g
- https://developer.tuya.com/en/demo/python-iot-development-practice

## Render

1. Завантажте репозиторій у свій Git-провайдер і підключіть до Render через **New → Blueprint**, використовуючи `render.yaml`.
2. Blueprint створює **платний Web Service** з Persistent Disk 1 GB. Перевірте актуальну вартість перед створенням ресурсів.
3. Введіть секрети й Device ID у змінні середовища, перевірте endpoint. Змініть назви за потреби.
4. Файл БД буде `/var/data/socketstat.db`; `/var/data` — точка монтування диска.
5. Відкрийте HTTPS-адресу сервісу та авторизуйтеся.

Не використовуйте free-сервіс із тимчасовою файловою системою: він може засинати й не зберігатиме SQLite після перезапусків. Не виносьте збирач в окремий Render-сервіс: Persistent Disk не спільний між сервісами. Диск також означає коротку перерву під час деплою; пропущені хвилини залишаться невідомими.

`GET /healthz` — відкритий liveness endpoint без даних розеток. Він перевіряє БД і роботу задачі збору, але не вважає збій Tuya причиною перезапуску сервісу. `GET /api/dashboard?hours=24` — захищений API (1 ≤ hours ≤ 336). Панель і API мають `Cache-Control: no-store`. Basic Auth слід використовувати через HTTPS; Render надає HTTPS на публічній адресі.

Для резервних копій використовуйте SQLite backup API / команду `.backup`, а не просте копіювання лише основного файлу активної WAL-бази. Видалені записи звільняють місце для повторного використання; файл БД не обов’язково зменшується. 14 діб — строк зберігання робочої історії, а не гарантія стирання з резервних копій платформи.

## Як інтерпретувати історію

Один запис описує хвилинний слот UTC. Інтервали однакових станів об’єднуються; стан не переноситься через пропущені хвилини. Унікальний ключ `(device_id, scheduled_at)` захищає від повторного запису. У БД — Unix UTC, у панелі — `Europe/Kyiv` з урахуванням літнього часу.

Тривалість — оцінка за дискретними перевірками, межі округлено до хвилинних слотів. Фактичний час відповіді збережений окремо як `checked_at`. Перший слот після запуску може бути неповним. Недоступність через Tuya може відображатися із затримкою heartbeat, і не доводить відключення електроенергії: причиною також може бути Wi-Fi, домашній інтернет чи Tuya. Статус на картці стає невідомим після 120 секунд без свіжого спостереження. На графіку пропущений поточний слот одразу відображається як невідомий до завершення перевірки.

Якщо інтервал впирається в край видимого періоду, його справжній початок або завершення можуть бути за межами графіка. Безперервний офлайн, розділений пропуском даних, рахується як два спостережувані інтервали.

Прогнозування поки не реалізоване. Двотижнева історія дозволяє почати з аналізу коротких повторень; для довших закономірностей знадобиться окреме рішення про збереження агрегатів.

## Перевірки

```sh
pip install -r requirements-dev.txt
python -m pytest -q
```

Тести використовують тимчасові БД та підмінені HTTP-відповіді. Перевіряють пропуски, межі інтервалів, очищення, незалежність двох розеток, підпис запитів, оновлення токена та авторизацію. Для перевірки реального інтегрування потрібні ваші облікові дані Tuya; не передавайте їх у чат.

Додаткові перевірки групування графіків (не потрібні для запуску сервісу, Node.js 18+):

```sh
node --test tests/charts.test.cjs
```

Вони перевіряють поділ за київською північчю, часткові хвилини, пропуски, перехід на літній/зимовий час і побудову панелей без даних. Тижневий розклад використовує лише вибраний діапазон; решта тижня показана штрихуванням.
